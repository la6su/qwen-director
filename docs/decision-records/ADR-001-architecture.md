# ADR-001: собственное ядро с заменяемыми исполнителями

- Дата: 2026-09-08.
- Статус: предложено для реализации; пересмотреть после discovery.
- Область: QwenDirector, local-first, multi-node execution.

## Контекст и доказательная база

Нужны независимые от модели шоты и ассеты, локальные GPU, ручные утверждения и восстановление после сбоев. Публичный UX-референс [MiniMax-H3-Director-Cut-Studio](../reference-director.md) предоставляет идеи timeline, Shot Units, media pool и ComfyUI workflow, но его текущие commit/licence details требуют локальной проверки. Ниже сравниваются стратегии, а не заявляется полная совместимость.

## Варианты

| Критерий | Аккуратный локальный форк Director Studio | Собственный QwenDirector |
|---|---|---|
| Первое демо | Потенциально быстрее, если существующий UX подходит | Нужно реализовать минимальный путь |
| Модельная независимость | Требуется проверить и отделить model-specific code | Задаётся доменом и adapter contract |
| Multi-node и восстановление | Нужно проверить текущие очереди и протокол | Lease, fencing и reconcile проектируются сразу |
| Локальная работа | Аудит сетевых вызовов, auth и хранения | Local-only по умолчанию |
| Поддержка | Стоимость сопровождения расхождений с upstream | Полная ответственность за продукт и тесты |
| Лицензия | До аудита заимствование кода недопустимо | Собственный код; зависимости также проверяются |

## Решение

Рекомендуется собственное ядро QwenDirector: Vue 3/Vite + Node.js LTS/Fastify, PostgreSQL как durable state/queue, локальный файловый blob store, отдельные TypeScript workers. Основание — обязательные требования к исполнению и владению данными, а не предположение, что Director Studio их не поддерживает.

Fastify выбран как компактная HTTP-граница с валидацией схем; Node.js — единый runtime backend и worker с удобными сетевыми интеграциями. Это проектный выбор, не результат performance benchmark. Альтернативы: более тяжёлый framework оправдан при росте команды; отдельный брокер — при измеренном bottleneck очереди. SQLite подходит для прототипа, но создаёт лишний путь миграции для сетевого координатора. Python не становится вторым backend.

## План заимствования и миграции

1. Получить локальный checkout Director Studio, origin, commit и license/NOTICE. Без checkout аудит остаётся открытым.
2. Составить карту UI, доменных сущностей, провайдеров, persistence и сетевых обращений. Не запускать неизвестный код до review.
3. Проверить один сквозной локальный сценарий и оценить объём изменений для model independence, leases, cancellation и offline operation.
4. Переносить удачные UX-идеи и workflow mappings через собственный контракт. Код переносить только при совместимой лицензии с сохранением attribution и перечнем источников.
5. Если есть пользовательские проекты форка: read-only importer → dry-run отчёт → mapping projects/scenes/shots → копирование ассетов с hash → импорт provenance. Неизвестные поля сохранять в namespaced `sourceMetadata`; не придумывать model digest или seed.
6. Сверить количество сущностей, порядок шотов, связи, размеры и hashes. Оригиналы оставить неизменными; rollback — удалить только новый импорт по import batch ID.
7. Прекратить dual-write после приёмки; форк оставить архивом или отдельным экспериментальным UI. Не поддерживать две основные очереди одновременно.

## Условия пересмотра

Форк можно предпочесть, если локальный аудит подтверждает лицензию, отсутствие обязательного облака, переносимый домен и возможность подключить собственный execution backend с меньшей оценённой стоимостью. Discovery должен дать таблицу соответствия требованиям и оценки обеих стратегий. До этого реализация следует выбранному собственному ядру.

## Последствия

Потребуется собственный минимальный UX и миграции. Зато библиотека, версии промптов и очередь не наследуют неизвестных ограничений upstream. Центральный API/БД остаётся точкой отказа на ранних этапах; workers переживают его недоступность через журнал/reconcile, но новые назначения при остановке координатора не выполняются.
