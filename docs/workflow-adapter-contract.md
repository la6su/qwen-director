# Контракт workflow adapter v1 (проект)

## Структурированные заметки continuity для шота

Planner Assist может читать необязательный объект `source_metadata.directing.montage` из каталога шотов. Поддерживаемые поля: `shotScale` (`detail`, `cu`, `mcu_1st`, `ms_2nd`, `wide`, `extreme_wide`), `cameraAxisDeg` (0–359), `screenDirection`, `actionPhase`, `focalCenter` (проценты 0–100), `lightDirection`, `colorBridge` и `motionTempo`. Контракт валидирует диапазоны и ограничивает длину текстовых заметок. Импортированные metadata вне этого namespace не интерпретируются как режиссёрские факты.

Эти заметки описывают постановочный план, но не подтверждают содержимое референсного изображения. Если сведения отсутствуют или некорректны, planner должен явно оставить проверку неприменимой/требующей просмотра, а не выводить ракурс, вектор, фазу или темп из свободного текста. Контракт не принимает отметку `consistent`, если для соответствующей проверки нет нужных typed montage fields у текущего и каждого доступного соседнего шота. Audit остаётся рекомендацией для режиссёра. Planner receipt сохраняет компактный snapshot и hash текущего и соседних шотов, их brief-секций, длительности, continuity notes, reference AssetVersion IDs/roles и montage metadata; на создании job API пересчитывает snapshot под блокировкой строк каталога и сверяет оба значения. Несовпадающий или устаревший контекст отклоняется. Поля можно редактировать во вкладке «Режиссура».

Это спецификация будущего TypeScript-контракта, не готовый SDK. Реализация разместится в `packages/contracts` и `packages/workflow-adapters`. JSON Schema проверяет входы/выходы; неизвестный major отклоняется, minor допускает только согласованные добавления.

## Переносимый вход

```ts
type AssetRef = { assetVersionId: string; sha256: string; role: string };
type GenerationSpec = {
  schemaVersion: '1.0';
  shotId: string;
  promptRevisionId: string;
  modality: 'text' | 'image' | 'video' | 'audio' | 'previs';
  inputs: AssetRef[];
  intent: { prompt: string; negativePrompt?: string };
  output: { mimeType: string; width?: number; height?: number;
    durationSeconds?: number; fps?: number };
  seed?: number;
  adapterOptions: Record<string, unknown>; // namespaced, валидирует адаптер
};
```

GenerationSpec не содержит IP, device ordinal или локальных путей. ExecutionPlan отдельно фиксирует adapter ID/version, workflow ID/digest, model IDs/digests, requirements (VRAM/disk/concurrency), resolved parameters, retry budget, output limits и hash GenerationSpec. Node выбирается по совместимости. Любое изменение содержательных параметров меняет plan hash и требует approval.

## Интерфейс исполнителя

| Метод | Поведение |
|---|---|
| `describe()` | Версии контракта, modalities, options schema, support cancel/lookup |
| `probe(context)` | Локальные capabilities, модели/digests, backend version и health |
| `validate(spec)` | Проверка входов и совместимости без генерации |
| `plan(spec, capabilities)` | Полный execution plan и оценка ресурсов; неопределённости явно |
| `prepare(plan, context)` | Проверка файлов/hash, backend и ресурсов; без submit/скачиваний |
| `submit(plan, attemptKey)` | Запуск, durable receipt с externalRunId/correlation key |
| `lookup(attemptKey, receipt?)` | Найти существующий запуск или вернуть unknown/absent |
| `poll(receipt)` | queued/running/succeeded/failed/cancelled/unknown и progress |
| `cancel(receipt)` | requested/confirmed/unsupported; не обещает мгновенную остановку |
| `collect(receipt)` | Output manifest, локальные staging-файлы и provenance |
| `cleanup(receipt)` | Только временные файлы этой попытки по политике retention |

Context даёт scoped asset reader, staging writer, logger, abort signal и ссылки на секреты. Адаптер не изменяет Job/Approval/Asset напрямую. API принимает результаты после проверки fencing. Abort signal останавливает локальное ожидание, но не доказывает отмену backend job.

## Envelope и результат

Каждая команда worker содержит `protocolVersion`, `jobId`, `attemptId`, `attemptKey`, `fencingToken`, `planHash`, `leaseExpiresAt`. Heartbeat включает sequence number; progress может повторяться и не определяет окончательный статус.

Output manifest: `schemaVersion`, job/attempt IDs, plan hash, список `{logicalName, mimeType, byteSize, sha256, stagingHandle}`, фактические параметры и provenance. Staging handles не разрешают произвольный доступ к файловой системе. API проверяет ownership, hash, размер, ожидаемый media type и лимиты; commit создаёт immutable AssetVersion. Пустой или частичный вывод не считается success, если это прямо не разрешено output schema.

Provenance обязателен: input asset hashes/revision IDs, prompt revision, adapter/backend versions, model/workflow digests (или explicit unknown), requested/effective seed и параметры, external run ID, node/device, времена submit/start/end, выходные hashes. Prompt snapshot хранится локально с контролем доступа; секреты никогда не включаются.

Project-level source media — отдельные ссылки на `AssetVersion`, не shot inputs и не generation outputs. Для каталога используются роли `master_audio`, `reference`, `source_video`, `deliverable`; API проверяет согласованность MIME для master audio и source video. Проектный export включает эти ссылки и их provenance.

Если job создаётся из принятого предложения Planner Assist, UI передаёт `plannerDecision` только пока восемь полей формы совпадают с предложенными. Receipt содержит hash секций, ID project-bound planner session и provenance модели/инструментов. API повторно вычисляет hash и сверяет секции и provenance с сохранённым assistant turn в этой сессии; только проверенный receipt попадает в immutable `jobs.plan_json.plannerDecision`. Ручная редактура сбрасывает применимость receipt, а отсутствие receipt не блокирует обычный ручной job.

Planner Assist возвращает также advisory `continuityAudit`: семь аспектов стыка (крупность, угол камеры, экранное направление, фаза действия, центр внимания, свет/цвет и темп) со статусами `consistent`, `review` или `not-applicable`, плюс общий статус. Это не технический PASS и не approval: без соседних shots API формирует `not-enough-context`; при наличии контекста модель обязана назвать основания краткими заметками на русском языке и не утверждать измерений, которых нет во входных данных. Audit входит в decision hash, отображается в истории диалога и сохраняется в job receipt вместе с исходным предложением.

## Ошибки, повтор и отмена

Коды: `INVALID_INPUT`, `UNSUPPORTED`, `RESOURCE_UNAVAILABLE`, `BACKEND_UNAVAILABLE`, `OOM`, `DISK_FULL`, `TIMEOUT`, `OUTPUT_INVALID`, `CANCEL_UNSUPPORTED`, `EXECUTION_UNKNOWN`. Error envelope включает stage, retryable hint, safe message, backend run ID и диагностическую ссылку без секретов. Решение о retry принимает оркестратор.

Автоповтор допустим при подтверждённом отсутствии запуска либо подтверждённой терминальной ошибке и оставшемся approved budget; backoff и max attempts хранятся в плане. При неизвестном результате submit — lookup/reconcile, затем needs_attention, если доказательств недостаточно. Разные attempts используют разные attempt keys; повтор submit одной попытки обязан искать уже начатый run. Адаптер без backend idempotency объявляет это ограничение и не маскирует его.

Для установленного локального ComfyUI submit использует UUID `attemptId` как `prompt_id` (формат и поддержка подтверждены исходником запущенной локальной версии). При сетевом сбое, HTTP 5xx или неполном ответе адаптер делает только read-only lookup `/api/jobs/{prompt_id}`. Найденная задача продолжает обычный poll; если lookup не подтверждает её наличие, worker помечает attempt `unknown`, job — `reconciling`, сохраняет fencing и не удаляет attempt-scoped input-файлы, нужные потенциально выполняющемуся workflow. Это состояние требует ручной сверки; автоматического resubmit нет. HTTP 4xx от `/prompt` считается явным отказом.

## ComfyUI mapping

Workflow template хранится как версионированный JSON с digest и allowlisted custom nodes. Mapping связывает поля GenerationSpec с конкретными node inputs; эти node IDs не попадают в Shot. Prepare проверяет наличие нужных custom nodes, точных имён файлов в live dropdown ComfyUI для поддерживаемых loader nodes (`UNETLoader`, checkpoint/CLIP/VAE, LoRA и H3 PDD), допустимых путей и форматов. Если runtime не отдаёт каталог файла, preflight fail-closed; отсутствующий файл не должен обнаруживаться только после постановки job в очередь. Никаких auto-install custom nodes, downloads или произвольных HTTP URL из пользовательского workflow.

Профили workflow сохраняются как неактивные кандидаты. `POST /preflight` и `POST /test` проверяют graph/runtime без изменения active state. Отдельная активация revision сначала повторно проходит live schema/model/LoRA preflight и только затем разрешает использовать граф для новых jobs; новый профиль не становится выбором по умолчанию при сохранении.

Для MiniMax H3 Ref2VA API сохраняет director fields и скомпилированный prompt в immutable job plan snapshot. Локальная конвенция делит текст на шесть смысловых полей, назначает reference assets ограниченным ролям и отдельно передаёт soundscape и музыку; нативный H3 узел получает обычный текстовый prompt, не schema-validated объект. H3 длительность UI округляется к кадрам `17k+5` при 24 fps. Монтажные проверки остаются advisory и не меняют workflow graph или sampler параметры.

Для `MiniMaxH3ImageToVideo` один связанный `first_frame` означает I2VA и требует ровно один AssetVersion с ролью `first-frame`; наличие `last_frame` задаёт FL2VA и требует согласованную пару. I2VA компилируется с alignment line и базовыми секциями `integrated_multimodal_description`, `overall_soundscape`, `non_diegetic_music`. H3 preflight до создания executable job проверяет класс генератора, prompt injection binding и точные имена моделей/LoRA/PDD по текущему `/object_info`. `smoke:h3-worker-e2e` проходит весь manual approval → worker → mock ComfyUI protocol → CAS → AssetVersion manifest путь; он не отправляет задачу в реальный ComfyUI и не расходует GPU.

Comfy UI workflow import проверяет primitive widget types и enum values по текущему `/object_info`; graph со stale widget order отклоняется до сохранения profile. Поддержка plugin `MiniMaxH3Director` требует отдельной versioned boundary и явного remapping embedded timeline references в immutable AssetVersion inputs.

Submit сохраняет correlation key, если backend поддерживает metadata, и возвращённый prompt/run ID в локальном журнале. Точные endpoints и возможности history/interrupt проверяются по установленной версии в discovery. Для глобального interrupt нужен выделенный экземпляр; невозможность адресной отмены явно видна UI. Outputs копируются из разрешённого backend output root с защитой от traversal/symlink escape, затем загружаются в asset API.

### Локальный H3 RefMod I2V boundary

Профиль с `referenceBindings.mode = "refmod-i2v"` фиксирует API-format graph с одним `MiniMaxH3ImageToVideo`, `MiniMaxH3RefModsLoader`, `MiniMaxH3RefModApply`, `RandomNoise` и `SaveVideo`. Валидация требует два разных доступных RefMod names и связанные `LoadImage` bindings; профильный preflight сверяет их с dropdown inventory ComfyUI. Worker загружает только image AssetVersion refs, предназначенные для кадров/окружения; actor/vehicle identity задаются именами immutable RefMods из profile snapshot. `LoadImage` refs инъецируются в связанные узлы и остаются tensor links на входах `first_frame`/`last_frame`. Node IDs остаются только в graph/profile boundary, а не в Shot. Plan snapshot сохраняет graph hash, RefMod names, bindings и AssetVersion IDs; job проходит обычные approval, lease/fencing и CAS commit.

### Локальный H3 FL2VA boundary

Для прямой first/last-frame генерации используется отдельный `fl2va-i2v` boundary на `MiniMaxH3ImageToVideo`, без RefMod nodes. В API graph оба входа `first_frame` и `last_frame` должны быть подключены к разным `LoadImage`; profile сохраняет эти два node binding в этом же порядке и hash неизменённого graph. На job references обязательно передаются ровно два изображения с явными ролями `first-frame` и `last-frame`; Worker загружает оба в ComfyUI и назначает файлы в порядке ролей, не полагаясь на порядок медиатеки. Остальные аудио, видео и изображения для этого boundary запрещены.

FL2VA принимает длительность от 124 кадров на сетке `(frames - 5) % 17 === 0` при 24 fps. Prompt compiler добавляет alignment line: First Frame на `0.00 s`, Last Frame на `frames / 24` с округлением до двух знаков. Preflight сверяет API schema, обязательные nodes и доступность LoRA; Ref2VA Pika Flex LoRA запрещена на FL2VA graph, а профиль обязан содержать подходящий FL2VA model stack. Профиль не становится default и проходит обычную ручную активацию; generation job сохраняет оба AssetVersion, alignment prompt, graph hash и параметры в immutable plan, затем использует общие approval, attempt/lease/fencing, cancellation, output collection и CAS lineage.

### Локальный H3 I2VA boundary

`MiniMaxH3ImageToVideo` с единственным подключённым `first_frame → LoadImage` является I2VA; с двумя различными подключениями `first_frame` и `last_frame` — FL2VA. I2VA profile автоматически связывает ровно один loader с `first_frame`, а job требует ровно один image AssetVersion с ролью `first-frame`. FL2VA сохраняет существующий контракт ровно двух кадров с ролями `first-frame` и `last-frame` в том же порядке, что и node inputs. Оба режима отвергают отсутствующий/неверный first frame, одинаковые frame nodes и графы с несовместимыми RefMod nodes. Для I2VA и FL2VA число кадров должно быть не меньше 56 и лежать на сетке `17k+5`.

Базовые H3 режимы I2VA/FL2VA используют prompt compiler с первой строкой alignment (только для keyframe mode), затем в точном порядке `integrated_multimodal_description`, `overall_soundscape`, `non_diegetic_music`. Ref2VA остаётся отдельной шестисекционной схемой, а `compileDirectorPrompt` предназначен для нережимных workbench briefs и не используется для H3 video prompt. Компиляция не доказывает качество результата; sampler/profile revision и ручное approval остаются неизменными.

Локальный `inspectH3Prompt` проверяет секции, последовательность `[Shot N]`, наличие и диапазон таймкодов склеек, допустимую кадровую сетку, режимные alignment lines и пределы явно использованных reference labels. UI показывает результат до submit; API выполняет ту же проверку после compilation и отклоняет контрактные ошибки до создания durable job. Версия инспектора, режим, число кадров и findings входят в immutable plan/hash. Для RefMod используется та же шестисекционная Ref2VA prompt schema, что и для R2V. Проверка не утверждает художественную состоятельность, причинность действия, физику либо качество сгенерированного видео.

Live H3 preflight выбирает `MiniMaxH3ImageToVideo` для обоих keyframe boundaries (`i2va-i2v` и `fl2va-i2v`), а `MiniMaxH3ReferenceToVideo` — для R2V/VEDA. Для H3 graph обязателен prompt binding, который worker умеет инъецировать напрямую или через `PrimitiveStringMultiline`/`PrimitiveString`; иначе профиль отклоняется до создания исполняемого job. Помимо class/input/link validation, preflight сверяет literal model filenames для поддерживаемых Comfy loader nodes с их live `/object_info` dropdown options; отсутствие каталога — явная ошибка, а не пропуск проверки. Это ранняя проверка доступности, не проверка загрузки весов в GPU и не generation success.

### H3 R2V bindings и двухэтапный VEDA boundary

Для обычного H3 R2V профиля явные `imageNodeIds`, `audioNodeIds` и `videoNodeIds` должны соответствовать нумерованным входам `ref_images.ref_image_N`, `ref_audios.ref_audio_N` и `ref_videos.ref_video_N` узла H3: слоты идут подряд с нуля, каждый loader должен быть upstream именно от своего слота, а число передаваемых AssetVersion должно точно совпадать с числом bindings. Для видео разрешена промежуточная обработка (например, `LoadVideo` → `GetVideoComponents` → H3), но связь должна доходить от указанного loader до соответствующего сокета. Незаполненные или лишние слоты отклоняются до `awaiting_approval`; placeholder path из шаблона не считается референсом. Входы `ref_video_audios.*` пока не поддерживаются и отклоняются при подключении, так как контракт не содержит семантики bindings для аудио из видео.

Для `video_mmh3_r2v_2Stage-VEDA` API-граф должен содержать один `MiniMaxH3ReferenceToVideo`, два `RandomNoise`, `MMH3UltimateUpscale`, `VedaSparseAttention` и два `VHS_VideoCombine`. Boundary проверяет upstream conditioning и latent второго прохода, отдельный промежуточный output и финальный saver после `VAEDecode` от upscaler. Упорядоченные `LoadImage` refs связываются с последовательными H3 slots `ref_images.ref_image_0..N`; каждый слот должен вести ровно к одному уникальному loader. Worker обновляет prompt в `PrimitiveStringMultiline`, сохраняя `StringConcatenate` prefix; длительность задаётся через подключённый `PrimitiveFloat` и графовый aligner, resolution — через `ResolutionSelector` и его megapixel input. Изменение sampler/LoRA/attention/upscale параметров остаётся частью immutable graph revision. При заданном seed одинаковое значение применяется к обоим noise nodes; без seed сохраняются значения из графа. Collect сохраняет только финальный `VHS_VideoCombine`, не промежуточное видео. Runtime preflight требует VEDA/upscale и VHS nodes, затем проверяет LoRA inventory.

Workbench `refmod-create` сохраняет созданный RefMod как sidecar-ассет: worker находит ровно один файл `<expectedName>.safetensors` в локальной `/refmods/library`, проверяет `realpath` относительно явно настроенного `QWEN_COMFY_REFMODS_ROOT`, regular-file status и верхний лимит размера, после чего возвращает bytes через обычный fencing/CAS result path под слотом `refmod`. Неоднозначный, отсутствующий или выходящий за разрешённый каталог путь завершается ошибкой. `smoke:refmod-collector` проверяет сбор и path containment; DB-backed `smoke:refmod-durable-e2e` проходит mock Comfy `/object_info`/`prompt`/`history`/`refmods/library` → worker attempt с fencing → output upload → CAS AssetVersion → durable manifest. Он не проверяет создание RefMod самим GPU custom node и его содержательную валидность.

Успешный ComfyUI collect добавляет в durable attempt manifest `executionEvidence` (`qwendirector-comfy-execution-evidence/v1`): job/attempt/plan identity, profile ID и исходный profile graph hash, hash фактически отправленного графа после инъекции входов, измеренные из job plan параметры (размер, кадры, seed), доступные поля `/system_stats` и `qualityControl.status=not-performed`. Во время poll executor дополнительно агрегирует `minimumObservedFreeBytes` примерно раз в 10 секунд и в конце попытки. Это device-wide наблюдение за всем окном попытки (включая другие процессы и возможное ожидание в ComfyUI), не память, доказанно занятая именно этим workflow, и не точный VRAM peak. Оно пригодно для последующей статистики и ручного анализа, но не для автоматического admission без отдельной калибровки. Весь receipt — provenance одного запуска, не qualification профиля и не оценка картинки/звука. Отсутствие `/system_stats` не блокирует генерацию: runtime evidence получает `status=unavailable`; последующие poll-снимки могут добавить частичное наблюдение, если endpoint восстановится. Профиль считается художественно проверенным только после отдельного человеческого просмотра; output AssetVersion и SHA-256 связаны с тем же manifest обычным fenced commit.

Quality metadata профиля вычисляется по фактическому `BasicScheduler.steps` (включая поддерживаемые switch/primitive links), связанному `ManualSigmas` schedule и установленной LoRA. Число шагов для ManualSigmas равно `sigma_count - 1`; при нескольких connected sampler stages число суммируется, только если все явные расписания распознаны. Несовпадение шагов и LoRA отображается как `unknown`; label LoRA сам по себе не подтверждает sampling steps. UI показывает извлечённый count рядом с именем профиля, но это не quality approval. FL2VA LoRA применима только к FL2VA I2V workflow, Ref2VA — только к соответствующему Ref2V workflow.

## Приёмочные сценарии

Mock обязан детерминированно воспроизводить success, error, timeout, duplicate submit, delayed completion, lost submit response, unsupported cancellation и corrupt output. Contract tests проверяют отсутствие двойного commit, отказ stale fencing, повторяемость lookup, выход без секретов и отсутствие внешнего egress. Реальный adapter проходит тот же набор применимых сценариев плюс один утверждённый локальный smoke workflow.

Первые backend targets реализуются в `packages/workflow-adapters/src/backend.ts`: локальный `LlamaCppAdapter` (text) и `ComfyUiAdapter` (image/video/audio/previs), endpoints задаются локальной конфигурацией. Оба сначала выполняют `probe`; llama adapter читает `/v1/models`, ComfyUI adapter — `/system_stats` и устройства. `router.ts` выбирает только reachable backend с заявленной modality. Adapter не скачивает модели и отклоняет внешний `workflowUrl`.

Comfy MCP можно использовать как optional control plane для local discovery/search workflows, submit graphs и получения outputs через stdio. Cloud connection и credits не включаются в local-first baseline; durable queue, approvals, provenance, fencing и storage остаются в QwenDirector. Источник: [Comfy MCP](https://comfy.org/mcp/).

## H3 качество и длительность

UI передаёт длительность как секунды. Для обычных H3 profiles worker принимает зафиксированное число кадров; VEDA-профиль выравнивает его в последовательность `17k+5` при 24 fps (5 секунд дают 124 кадра) и связывает с graph duration input. Разрешение, seed и references являются job inputs; sampler, scheduler, LoRA, steps, VAE и codec принадлежат immutable workflow profile и не должны неявно изменяться адаптером. Quality-профили с большим числом steps активируются отдельно после проверки VRAM, а не автоматически.

## AIMixer MiniMaxH3Director timeline v5

`packages/workflow-adapters/src/minimax-director-timeline.ts` разбирает `timeline_data` AIMixer как read-only вход. Поддерживается только `version: 5`; неизвестная версия, пустой список сегментов, повторяющиеся ID, пересекающиеся диапазоны и некорректное число кадров отклоняются. Результат сохраняет исходный JSON snapshot, упорядоченные диапазоны кадров, локальные prompts, task type, continuity marker и media с областями применения. Media identity включает семантическую роль: `startImage` становится `first-frame`, `endImage` — `last-frame`, обычные картинки — `picture`; input-only resolver не требует сопоставлять output/temp paths.

UI предоставляет отдельный импорт файла workflow в выбранную сцену. Пользователь сопоставляет каждый `input` media с уже существующим AssetVersion; сервер проверяет UUID, наличие и MIME, после чего транзакционно создаёт `shot_import_batches`, один draft shot на сегмент и `shot_reference_assets` по scope и роли. Одна CAS-версия может занимать несколько семантических слотов одного шота, например First Frame и Last Frame. Исходный timeline digest и media mapping digest обеспечивают идемпотентное повторение; тот же source с другим mapping возвращает conflict. Сегменты хранят frame range, fps, canvas, global/local/negative prompts, role-aware reference bindings и continuity в `source_metadata`; исполняемый prompt объединяет global и local prompt. UI отправляет сохранённые ordered roles в обычный QD job, пока оператор не изменит список референсов.

Импорт только подготавливает и выбирает первый shot. Он не создаёт jobs, не активирует профиль и не отправляет workflow в ComfyUI; каждый job остаётся под обычным manual approval и текущей проверкой workflow profile. Video/audio references сохраняются как AssetVersion связи, однако не становятся автоматически нодами H3: необходимое workflow binding настраивается отдельно. Импорт принимает только ComfyUI workflow UI JSON с `MiniMaxH3Director` и embedded timeline v5. Файл workflow не сохраняется как исполняемый graph, а model/LoRA/sampler/runtime widgets не переносятся в QD profile.

`input` assets можно выбрать из Media Pool или импортировать прямо из файла в браузере: API проверяет лимит 100 MiB и CAS content hash, а importer проверяет MIME по виду reference. Также можно восстановить refs локальной командой `npm run import:aimixer-references` (dry-run по умолчанию; `--commit` работает, когда ComfyUI refs доступны). Физические файлы с несколькими семантическими ролями читаются и импортируются один раз, а вывод содержит отдельные role bindings на один AssetVersion. Пути `output`/`temp` timeline не импортируются как входные refs. Схема импорта требует миграций 021, 023 и 024 (роль First/Last Frame и повторное связывание одного AssetVersion в разных role slots). Parser и исходный snapshot сохраняют исходные кадры/порядок сегментов, но пока нет редактируемого preview/reorder UI и нет worker-side исполнения AIMixer graph.

Для восстановления references есть `npm run import:aimixer-references`: по умолчанию он только скачивает refs с loopback ComfyUI, проверяет статусы/размеры и печатает результат. Режим `--commit` доступен только при наличии всех references; он передаёт их через локальный `/v1/assets/import`, требует `QWEN_IMPORT_ACTOR` и возвращает mapping SHA-256 → AssetVersion ID. `COMFYUI_URL` ограничен localhost. QwenDirector endpoint берётся из `QWEN_API_URL`, затем `QWEN_API_BASE_URL`, или по умолчанию `http://127.0.0.1:4310`; endpoint также ограничен localhost. Импортирует каждый blob отдельно с content dedupe; связывание с shot plan остаётся следующим отдельным шагом.

## ComfyUI UI-workflow conversion

`POST /v1/workflows/convert` получает `object_info` живой ComfyUI, переводит UI JSON в API graph и проверяет типы классов, входов и links до сохранения профиля. Для widget значений сначала используется `widgets_values_named`, если тип значения соответствует schema. Если named-значение имеет неверный примитивный тип, допускается fallback на одноимённый positional UI widget только когда он сам типово совместим (`STRING`, `INT`, `FLOAT`, `BOOLEAN`); значения не приводятся принудительно. Если оба варианта не проходят schema, импорт завершается ошибкой. Это покрывает некоторые сохранённые custom-node graphs, где named metadata отстаёт от реального widget array, не ослабляя итоговую schema validation.

`ComfyWorkbenchExecutor` сохраняет `outputNodeId` для каждого файла ComfyUI. Профиль хранит явное отображение saver-node ID → типизированный slot. Для одного saver разрешён default slot первого контракта; несколько saver-узлов требуют полного отображения с уникальными slots до сохранения профиля/создания job. Collector проверяет, что каждый назначенный saver действительно вернул файл, и сохраняет slot, node ID и workbench provenance в каждом descriptor до worker CAS upload. UI workflow wizard показывает выбор Actor/Scene/Prop/Layout и отдельный slot для каждого saver. Это привязка по устойчивой топологии graph, не по случайному порядку Comfy output files; batch-файлы от одного saver наследуют его slot.

## H3 event plan v1

Опциональный `eventPlan` является частью Director prompt одного существующего шота и имеет контракт `qwendirector-h3-event-plan/v1`: `frameRate=24`, допустимый H3 `frameCount` и упорядоченные события с уникальным ID и диапазоном кадров `[startFrame,endFrame)`. События должны без пробелов/перекрытий покрывать весь delivery clip; каждый диапазон не короче пяти кадров и содержит наблюдаемое действие и достигнутое конечное состояние. Источник синхронизации хранится отдельно (`sourceRef`, `sourceTiming`); по умолчанию он отсутствует/непроверен, а `verified` требует явный source reference. Для причинной постановки событие может также записывать `entryState`, `trigger` и `continuityFromPrevious`; API фиксирует `eventCausalityReview` с пропущенными полями в immutable job plan. Этот отчёт проверяет только заполненность структуры, всегда указывает `semanticAssessment=not-performed` и не одобряет причинную убедительность автоматически.

Planner Assist получает компактный read-only event plan только текущего выбранного шота внутри `continuityContext` и добавляет `actionCausality` в тот же ответ continuity audit. При полном заполнении полей проверка может отметить структуру как заполненную, но обязана указать, что смысловая убедительность не оценивалась; неполный/некорректный план требует review, отсутствие плана — `not-applicable`. Это не вызывает дополнительную модель, не меняет шот и не запускает generation. Поле входит в существующий receipt/hash вместе с context snapshot. Старые receipts с семью проверками нормализуются с `actionCausality=not-applicable`; новые ответы модели обязаны возвращать все восемь проверок.

Компилятор добавляет временные фазы внутрь `[Shot 1]` и прямо задаёт непрерывность viewpoint: граница события сама по себе не является монтажной склейкой. Если общий prompt уже содержит несколько `[Shot N]`, event plan отклоняется, чтобы не смешивать таймлайн действия с многошотовым монтажом. UI и API используют один и тот же нормализатор; API валидирует повторно до создания job, а нормализованный plan и prompt входят в immutable `jobs.plan_json`/`plan_hash`. Изменение шота сохраняет event plan вместе с director prompt revision. Для не-H3 workflows план не компилируется и не передаётся исполнителю. Это временная разметка творческого плана, а не анализ аудио, доказательство lyric sync или гарантия точного поведения видеомодели.

При сборке Planner Assist получает до двух соседних `transitionReviews` в `continuityContext`: предыдущий → текущий и текущий → следующий шот. Контракт сравнивает только typed montage metadata: известный угол оси, грубую смену направления, горизонтальный сдвиг focal center, темп, крупность и наличие заметок о фазе/свете/цвете. Возможные расхождения получают статус `review`; отсутствующие данные — `unverified`; остальные значения лишь фиксируются как `observed`. Это структурный metadata-only preflight: он не видит изображение, не оценивает смысл совпадения фаз и не запрещает намеренный match cut или ритмический контраст. Полученные заметки входят в существующий continuity context hash и immutable planner receipt, поэтому изменение соседнего плана делает receipt устаревшим.

В planner receipt компилируется `qwendirector-director-timeline/v1` для окна предыдущий → текущий → следующий. Каждый segment — реальный shot из упорядоченного Scene/Shot каталога; его кадры начинаются с нуля окна. Event ranges сдвигаются на `segment.startFrame`, но остаются фазами действия внутри своего шота; входное состояние, trigger, связь с предыдущим событием, lyric/audio source и статус event causality сохраняются. Для planned shots длительность берётся из валидного H3 event plan; для остальных — округляется catalog `durationSeconds × 24`. `timingStatus` явно показывает unplanned/invalid event plan и расхождение плана с каталоговой длительностью. Join между соседними сегментами получает `transitionType=unspecified`, пока режиссёр не выберет переход. Timeline window входит в continuity context hash и durable planner receipt.

Тот же compiler строит полную read-only project партитуру из всех ordered scenes/shots для `GET /v1/projects/:projectId/timeline`. Ответ добавляет `directorTimeline` к существующему `scenes`, сохраняя прежнюю форму каталога. UI показывает кадр/таймкод окна, все шоты и их event phases, статусы неполной/некорректной временной разметки и metadata-only проверки стыков. Это производное представление текущего каталога, без отдельного persistent timeline и без записи или submit job. План работает в координатах 24 fps; сам по себе он не подтверждает синхрон с музыкальным master, намеренность склейки, качество кадра или длительность финального монтажа.

Перед H3 execution worker загружает каждую immutable reference в отдельную папку `qwendirector_refs/<attemptId>` с уникальным именем, включающим порядковый слот, AssetVersion ID и semantic role. Это предотвращает коллизию одинаковых basename между First/Last Frame, ролями и соседними попытками; в workflow подставляется путь, возвращённый ComfyUI upload endpoint. Так как ComfyUI v0.45.0 не предоставляет локальный HTTP endpoint удаления input-файлов, очистка доступна только при явно заданном `QWEN_COMFY_INPUT_ROOT`, указывающем на локальный input root, доступный worker-у. После завершившегося job worker удаляет только `qwendirector_refs/<attemptId>` и `qwendirector_refmods/<attemptId>`; очистка ошибка-изолирована и не меняет исход выполнения job. Без настройки или при аварийном завершении процесса файлы сохраняются; фонового stale-attempt GC пока нет.

## Qwen Image 2.1 image-edit workbench

Локальный `image_edit_QwenImage21.json` — ComfyUI UI workflow с одним `Image Edit (Qwen Image 2.1)` subgraph. Импортёр разворачивает definitions в API graph, сохраняя boundary links, значения виджетов и уникальные node IDs. Для корректного image-edit profile обязательны `LoadImage`, `TextEncodeQwenImage21`, `VAELoader` и `SaveImageAdvanced`, а sampler обязан получать latent исходного base image через `VAEEncode` или `VAEEncodeForInpaint`. Workflow wizard передаёт явно упорядоченный список `LoadImage` IDs. API требует полный список каждого image input ровно один раз, сохраняет его в immutable profile `reference_bindings`, а job snapshot передаёт тот же порядок worker-у. Worker назначает reference bytes точным IDs из списка. В UI первое выбранное изображение — база edit, последующие идут как дополнительные refs; сохранённые shot roles продолжают применяться. Первый `LoadImage` одновременно связан с `images.image_1` encoder-а и `VAEEncode.pixels`/`VAEEncodeForInpaint.pixels`, а VAE берётся из `VAELoader`. Локальный inpaint профиль может получить маску из того же base image через проверенную цветовую маску и `FeatherMask`; отдельный масочный asset в этом случае не нужен. Worker сохраняет связь prompt enhancer-а, если он используется, и иначе задаёт prompt напрямую в `TextEncodeQwenImage21`. Output собирается из saver node и получает slot `image`. Это отдельный workbench kind и не меняет H3 workflow contract.

`TextEncodeQwenImage21` (output 2) возвращает **пустой latent**, размер которого совпадает с первым reference; он не кодирует исходное изображение. Для image-edit первый `LoadImage` — base image: его пиксели кодируются `VAEEncode` либо `VAEEncodeForInpaint` с `VAELoader`, и `KSampler.latent_image` получает этот source latent (допустима переключающая нода, только если активна соответствующая VAEEncode-ветка). Inpaint путь обязан строить mask от того же base image через `ImageColorToMask`; optional `FeatherMask` может смягчать её край. Первый `LoadImage` остаётся `images.image_1` text encoder-а; следующие `LoadImage` — дополнительные references в том же порядке. При `resolution=0` encoder сохраняет reference size с округлением до кратного 32; положительное значение меняет размер encoder reference, но не заменяет VAE-кодирование base. Исходный graph не мутируется; выбранная ветвь входит в graph hash и immutable job snapshot. Профили, которые подают output 2 text encoder-а напрямую в sampler, не являются image-edit и должны быть отклонены preflight. Автоматическая подмена width/height не выполняется.

UI-only preview `ImageCompare` исключается при Comfy UI→API conversion и не становится исполняемым dependency/output. Saved input graph в `.data/comfyui-workflows/image_edit_QwenImage21.json` имел `custom_size` switch включённым, `resolution=0`, а custom latent dimensions `1659×948`; profile preparation выбирает encoder latent path, поэтому неиспользуемые custom canvas values не применяются. Candidate list включает и workbench profiles; их live schema test и activation проходят через workbench routes, а сам activation повторно проверяет runtime schema. Это подготовка workflow semantics, не доказательство качества картинки; перед первым job нужны корректные роли входных AssetVersion и обычное manual approval.

Для Qwen Image edit reference-порядок значим: первый `LoadImage` задаёт базовую композицию и output aspect; последующие референсы должны использоваться по назначенной роли. Один выбранный `AssetVersion` — один физический image input даже когда он связан с несколькими shot roles: UI схлопывает его role rows, выбирает наиболее конкретную роль (`actor`/`set`/`prop`/`layout`) и сохраняет порядок выбранных AssetVersion. Frame-only роли нормализуются к `picture` для Qwen edit. `compileQwenImageEditPrompt` добавляет роль `actor`/`set`/`prop`/`layout` и разрешает переносить явно запрошенную пространственную раскладку; запреты на сохранение исходной композиции, ракурса или света добавляются только когда соответствующее поле не переопределено режиссёром. Это важно для задач вроде `photo-room.jpeg` (база-комната) + `photo-monitors.jpeg` (layout рабочего стола) или обратной расстановки, когда точный стол должен стать основной композицией.

Порядок slot bindings для `image-edit` выводится из реальных links в `TextEncodeQwenImage21.images.image_1..N`, а не из порядка узлов в JSON-графе. UI показывает соответствие read-only; если сохранённые IDs противоречат encoder slots, validation отклоняет граф до создания job. Resolver `workbench-image-bindings` не зависит от Node.js API и безопасно используется браузерным wizard и серверным adapter. Проверки сохранённого профиля и его активация сначала применяют те же детерминированные `prepareWorkbenchGraph` нормализации, что используются при создании job; runtime preflight вычисляет и возвращает отдельно хэш исполняемого графа, сохраняя hash сохранённого профиля. Оставшийся в графе неиспользуемый `TextGenerate` не блокирует edit; если encoder prompt реально проходит через `TextGenerate`, его входные изображения должны покрывать все encoder references.

### Исторический кейс Qwen Image для прежней версии AI-Everywhere

Следующие наблюдения относятся только к старому исходнику и больше не являются handoff нового клипа.

Диагностика шума Qwen Image на AI-Everywhere: два дубля с одинаковыми prompt/seed/settings, включая повтор с `--disable-pinned-memory`, дали идентичные пиксели; OOM не было. При переключении только `TextEncodeQwenImage21.resolution` с `0` на `1024` выход стал чистым на эффективной сетке `1376×768`. На данном исходнике это изолирует чувствительность к эффективной сетке/reference token budget; не считать результат универсальным правилом для всех изображений. Для того же исходника настройка `resolution=1024` устраняла наблюдавшийся артефакт; для нового проекта это не готовый preset — сначала проверить выбранную геометрию и workflow на конкретных входах. Нельзя обвинять кратность 32 как таковую: входы уже были кратны 32.

Локальный текстовый рендер на Qwen Image 2.1 использует отдельный `image-generate` workbench: `UNETLoader`, Qwen CLIP/VAE, `QwenImage21Cache`, `TextEncodeQwenImage21`, `EmptyLatentImage`, sampler и `SaveImageAdvanced`. Этот путь не использует `QwenImageTextToImageApi` и внешние провайдеры. Для всех non-H3 workbench-типов кроме `image-edit` сохраняется обычный director prompt; запрещено применять к ним H3 Ref2VA-разметку (`subject_definitions`, `retention_analysis` и другие поля). `image-edit` использует отдельный Qwen edit compiler. Граф, seed и prompt входят в immutable job snapshot; результат остаётся в обычном approval/lease/CAS lifecycle.

В историческом проекте AI-Everywhere использовалась отдельная генерация Qwen Image вместо `character_01`. Это не инструкция для нового клипа; способ работы с новым героем определяется после получения нового brief. Утилита `H3RefModCreateFromFolder` сохраняет RefMod как побочный файловый результат в `models/refmods/<subfolder>` и может дать уникальное имя при совпадении. Это не ComfyUI output (`images`/`videos`), поэтому текущий worker collector автоматически не импортирует `.safetensors`. После проверки шести ракурсов RefMod нужно импортировать через локальный `/v1/assets/import` с SHA-256 и lineage от исходного кадра/ракурсов, затем связать с проектом; имя и фактический путь сохранённого файла следует читать из результата/лога узла, а не угадывать по запрошенному имени.

Subgraph importer ограничивает глубину восемью уровнями и должен завершать импорт ошибкой при некорректной топологии. Реальная проверка доступных классов/inputs требует ComfyUI `/object_info`. UI сохраняет импортированный graph как неактивный candidate и может включить его в durable image-edit job через immutable graph snapshot; job остаётся под обычным ручным approval. Runtime preflight и фактическое generation следует подтвердить на работающем ComfyUI/worker.
# Prompt routing for workbenches

`image-generate` treats the Director form's `prompt` field as the complete positive image prompt. Camera, action, composition, lighting, sound, and transition remain immutable shot metadata and must not be appended to that prompt by the worker. If the job has no Director prompt, the worker preserves the prompt already stored in the workflow graph. `image-edit` continues to use its compiled edit instructions and reference roles.

## Generated-image path gate for Actor/Scene/Prop/Layout workbenches

`validateWorkbenchGraph` now requires every `SaveImage`/`SaveImageAdvanced` output in `actor`, `scene`, `prop`, and `layout` graphs to have an upstream path through a recognized sampler (`KSampler`, `KSamplerAdvanced`, `SamplerCustom`, or `SamplerCustomAdvanced`). This rejects load-and-save passthrough graphs and disconnected sampler nodes before a candidate can be accepted. Runtime `/object_info` preflight remains responsible for actual socket compatibility and required input completeness; this static path check does not make an unprovided graph production-ready. Workbench image inputs still bind by explicit `LoadImage` order, and each saver retains an explicit output slot.

The same output-path check applies to Qwen Image edit/generate profiles. Image generation also requires the exact positive/negative conditioning outputs from `TextEncodeQwenImage21` to reach the sole `KSampler`, and its latent input to originate from `EmptyLatentImage`. The active local Qwen profiles were inspected read-only and match these connections. This does not replace `/object_info` socket validation.

## H3 sampled-output path gate

A regular H3 I2VA/FL2VA/Ref2VA profile is accepted only when one `SamplerCustomAdvanced` or `KSampler` is upstream of its `SaveVideo` node and both the H3 node and `RandomNoise` are ancestors of that same sampler. A RefMod profile additionally requires its `MiniMaxH3RefModApply` and `MiniMaxH3RefModsLoader` to feed the sampled path, with the apply node conditioned by H3. This rejects disconnected H3/noise branches and videos saved from an unrelated source. The two-stage VEDA boundary retains its dedicated path validation. Static reachability does not prove visual quality; runtime socket checks, manual approval, and result QC remain required.
